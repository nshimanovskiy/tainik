# Деплой Тайника на VPS

Итог: сервер работает по адресу `https://chat.ваш-домен`. Веб-версия открывается в браузере, десктоп подключается к `chat.ваш-домен`.

```
Интернет ──443──▶ ваш nginx (HTTPS, certbot) ──▶ 127.0.0.1:8787 ──▶ контейнер tainik (Node.js + SQLite)
```

Установка **не меняет файрвол** и **не трогает другие сайты nginx**: она добавляет отдельный файл `tainik.conf` и проверяет конфигурацию через `nginx -t`, а при ошибке откатывает изменения. Сервер Тайника слушает только `127.0.0.1`, снаружи к нему напрямую не подключиться.

## Что нужно на сервере

- Docker с `docker compose` и nginx. Certbot скрипт поставит сам, если его нет.
- A-запись `chat.ваш-домен` → IP сервера.
- Порт 80 должен быть доступен снаружи: через него Let's Encrypt проверяет домен.

## Установка

```bash
cd /opt/tainik/e2e-messenger        # папка проекта
sudo ./deploy/setup.sh chat.example.com you@example.com
```

Скрипт делает следующее:
1. запускает контейнер на `127.0.0.1:8787` (если порт занят, выберет свободный);
2. добавляет сайт в nginx с поддержкой WebSocket;
3. выпускает сертификат через `certbot --nginx` и включает редирект http → https;
4. включает ежедневный бэкап в 03:30;
5. в конце проверяет `https://домен/healthz`.

Скрипт можно запускать повторно. Уже выпущенный сертификат он не трогает.

### Если до этого запускалась прошлая версия скрипта (с Caddy)

Ничего чистить вручную не нужно: новая версия сама удалит оставшийся контейнер `caddy`. Данные сервера (том `tainik-data`) сохранятся. Если в прошлый раз включился ufw и вы его отключили, правила, добавленные скриптом, можно убрать:

```bash
ufw delete allow OpenSSH; ufw delete allow 80/tcp; ufw delete allow 443/tcp; ufw delete allow 443/udp
```

## Подключить клиентов

- **Главная страница и загрузки:** `https://chat.example.com` — описание и вкладка «Скачать» (файлы последнего выпуска с GitHub отдаёт ваш сервер, см. `RELEASES_REPO`).
- **Веб:** `https://chat.example.com/app`.
- **Десктоп:** в поле «Адрес сервера» введите `chat.example.com`. Можно и сразу собрать приложение с вашим адресом: `cd desktop && TAINIK_SERVER=chat.example.com npm run dist`. В GitHub Actions для этого задайте переменную `TAINIK_SERVER`.

### Восстановление из бэкапа

```bash
docker compose stop tainik
gunzip -k backups/tainik-ДАТА.db.gz
docker compose cp backups/tainik-ДАТА.db tainik:/data/tainik.db
docker compose start tainik
```

Бэкапы стоит копировать **за пределы сервера**. В базе нет переписки, но есть публичные ключи и аккаунты.

## Сайт nginx вручную

Если не хотите запускать скрипт, возьмите шаблон `deploy/nginx-site.conf`: замените `__DOMAIN__` и `__PORT__` (8787), положите в `/etc/nginx/sites-available/` и включите. Затем выполните `nginx -t && systemctl reload nginx && certbot --nginx -d домен`. Главное в шаблоне:
- заголовки `Upgrade` и `Connection` для WebSocket;
- `proxy_read_timeout 120s`, иначе nginx будет обрывать тихие соединения через 60 секунд;
- `X-Real-IP $remote_addr`, чтобы лимиты считались по реальному IP;
- `access_log off`.

## Обновление из GitHub (кнопкой)

Сервер можно обновлять прямо из репозитория. В нём один и тот же код и для деплоя, и для десктопных выпусков.

**Один раз на сервере** (из папки проекта):
```bash
sudo ./deploy/connect-github.sh ВЛАДЕЛЕЦ/РЕПОЗИТОРИЙ
```
Скрипт работает по шагам:
1. Создаёт ключ **только для чтения** и просит добавить его в **Settings → Deploy keys** репозитория (галочку «Allow write access» не ставить).
2. Подключает папку к репозиторию. Файлы проекта заменяются версией из GitHub, а `.env`, база, `backups/` и настройки TURN остаются на месте.
3. Создаёт пользователя `tainik-deploy` (вход root по SSH не нужен) и ключ для GitHub Actions и выводит значения для **Settings → Secrets and variables → Actions → New repository secret**: `DEPLOY_HOST`, `DEPLOY_PORT`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS`, `DEPLOY_KEY`. Этот ключ привязан к `deploy/remote-deploy.sh` (через `command=` и одно правило sudo) и может только запустить обновление: ни консоли, ни других команд, ни проброса портов. На сервере закрытая часть ключа не сохраняется.

**Обновление:** GitHub → **Actions → «Деплой сервера» → Run workflow**. Сначала проходят тесты, затем сервер делает бэкап, забирает код, пересобирает контейнер и проверяет `/healthz`, а в конце workflow проверяет сайт снаружи. Ход обновления виден в логе Actions.

Вручную на сервере: `./deploy/update.sh`, делает то же самое.

Чтобы обновление требовало подтверждения, включите в **Settings → Environments → production** правило «Required reviewers».

## Звонки через NAT (TURN)

Звонки между устройствами в одной сети или с «белыми» IP работают сразу. Если оба собеседника за NAT (мобильный интернет, офисная сеть), нужен ретранслятор TURN. Его запуск:

```bash
cd /opt/tainik/e2e-messenger
sudo ./deploy/setup-calls.sh
```

Скрипт делает следующее:
- генерирует секрет TURN и записывает его в `.env`;
- создаёт `deploy/turnserver.conf`;
- запускает coturn в сети хоста;
- перезапускает сервер Тайника.

Файрвол скрипт **не трогает**.

**Нужные порты:** `3478/udp`, `3478/tcp`, `49160–49200/udp`. Если у провайдера VPS есть файрвол в панели управления, откройте их там.

**Проверка:**
1. Выполните `./deploy/turn-test-credentials.sh`.
2. Введите выданные данные на странице [Trickle ICE](https://webrtc.github.io/samples/src/content/peerconnection/trickle-ice/).
3. Если в результатах появилась строка типа `relay`, TURN работает.

**Безопасность.** TURN пересылает только зашифрованные пакеты (DTLS-SRTP) и прослушать звонок не может. Учётные данные временные (12 часов) и не содержат имени пользователя. Пересылка во внутренние сети запрещена, журнал coturn отключён.

**Без TURN** сервер выдаёт клиентам публичный STUN `stun.l.google.com`. Чтобы отключить его, задайте в `.env` переменную `STUN_FALLBACK=` и выполните `docker compose up -d`.

## Уведомления в браузере (Web Push)

Работают сразу, настраивать ничего не нужно. При первом запуске сервер создаёт ключ VAPID и хранит его в базе (он попадает в бэкапы; если ключ потерять, браузерам придётся заново включить уведомления).

Когда устройство не в сети (вкладка закрыта), сервер отправляет пуш на адрес push-сервиса браузера: Google (Chrome, Edge, Яндекс), Mozilla (Firefox), Apple (Safari) или Microsoft. Содержимое пуша — тип события и имя отправителя — зашифровано ключом браузера (RFC 8291), текста сообщений в нём нет. Сервер отправляет запросы только на адреса этих сервисов, поэтому ему нужен **исходящий HTTPS** к ним.

| Переменная | Значение |
|---|---|
| `VAPID_SUBJECT` | Контакт для push-сервисов: `mailto:…` или `https://…`. По умолчанию берётся `ACME_EMAIL`, затем `https://DOMAIN` |
| `WEB_PUSH=0` | Выключить Web Push (уведомления будут только при открытой вкладке) |

## iPhone: подпись профиля

Страница `https://ваш-домен/ios` ставит Тайник на iPhone профилем с «закладкой». Без подписи iOS показывает его как «Не подтверждён». Подписать сертификатом Let's Encrypt вашего домена (он уже есть — его выпускает certbot):

```bash
sudo ./deploy/sign-profile.sh
```

Скрипт берёт у сервера профиль, подписывает его ключом сертификата (`/etc/letsencrypt/live/<DOMAIN>/`), проверяет подпись и цепочку и кладёт подписанный файл в данные контейнера — сервер сразу начинает отдавать его. iOS показывает «Подтверждён» и имя домена. Ещё скрипт ставит хук certbot (`/etc/letsencrypt/renewal-hooks/deploy/tainik-sign-profile.sh`): после продления сертификата профиль переподписывается сам, а `update.sh` переподписывает его после обновления.

Закрытый ключ читает только скрипт (под root); в контейнер он не попадает. Если сертификат лежит в другой папке: `sudo CERT_DIR=/etc/letsencrypt/live/имя ./deploy/sign-profile.sh`. Убрать подпись: `docker compose exec tainik rm /data/tainik-signed.mobileconfig` и удалить хук.

## Панель администратора

Страница со списком пользователей: статус «в сети» или «был(а) …», устройства, **текущий и последний IP каждого устройства**, дата регистрации, сколько сообщений ждёт доставки. Обновляется каждые 5 секунд.

Действия:
- **Удалить аккаунт** — безвозвратно: устройства пользователя отключаются и стирают у себя ключи и переписку, недоставленные ему сообщения удаляются, имя освобождается для регистрации. Для подтверждения нужно ввести имя пользователя.
- **Поставить / снять галочку** — официальная галочка рядом с именем, как в Telegram. Её сразу видят все собеседники пользователя (в списке чатов, в шапке переписки, при звонке) и он сам. У аккаунта `admin` галочка стоит по умолчанию — зарегистрируйте это имя сами, пока его не занял кто-то другой.
- **Заблокировать IP** — кнопка «блок» рядом с адресом или форма «Заблокированные IP». Подключения с этого адреса обрываются, новые не принимаются, сайт отвечает «Доступ запрещён». Панель администратора с заблокированного адреса остаётся доступной (чтобы нельзя было запереть самого себя). Блокировки хранятся в базе и переживают перезапуск. Учтите: у мобильных операторов один IP бывает у многих людей сразу.

1. Придумайте длинный пароль (не короче 12 символов), например: `openssl rand -base64 24`.
2. Допишите в `.env` на сервере:
   ```
   ADMIN_PASSWORD=ваш-пароль
   ```
   Адрес можно поменять переменной `ADMIN_PATH` (по умолчанию `/adminadminadmin`).
3. `docker compose up -d` — и откройте `https://chat.ваш-домен/adminadminadmin/`.

Как защищено: без `ADMIN_PASSWORD` панели нет (адрес отвечает «не найдено»). После входа выдаётся cookie на 12 часов (HttpOnly, Secure, SameSite=Strict), подписанная ключом из пароля — смена пароля завершает все сессии. После 10 неверных паролей с одного IP вход закрыт на 15 минут. Код и данные панели без входа не отдаются.

Для каждого устройства в базе хранится **последний IP**, с которого оно подключалось (только последний, без истории); его видит и сам пользователь в «Устройствах». В журнал IP не пишутся. Текст сообщений панель не видит: его не знает и сервер. Статус «в сети» в панели виден и у тех, кто скрыл его от собеседников. Пользователям вашего сервера стоит знать, что администратор видит их IP.

## Подписка «Тайник Премиум» (оплата криптовалютой)

Платная подписка оплачивается через [xRocket Pay](https://docs.xrocket.exchange/api/pay/pay-api-overview) — криптокошелёк в Telegram. Пока подписка даёт **фото профиля** и звезду рядом с именем; новые преимущества добавляются в коде. Пользователь открывает ⋯ → «Тайник Премиум», выбирает тариф, сервер выставляет счёт, и человек платит в боте @xRocket. Об оплате сервер узнаёт сам (подписанный вебхук), подписка включается через несколько секунд на всех устройствах пользователя.

1. В Telegram: [@xRocket](https://t.me/xRocket) → **Pay API** → **Создать приложение**. В настройках приложения: **API Version → Current** (обязательно — иначе вебхуки не придут), затем **🔑 API Token** и **🔑 Webhook Token**.
2. Допишите в `.env` на сервере:
   ```
   XROCKET_PAY_TOKEN=api-токен
   XROCKET_WEBHOOK_SECRET=webhook-токен
   PREMIUM_PLANS=30:3,90:8,365:30
   PREMIUM_CURRENCY=USDT
   ```
   `PREMIUM_PLANS` — тарифы «дни:цена» через запятую, цены — в `PREMIUM_CURRENCY`. Кроме неё можно платить валютами из `PREMIUM_PAY_CURRENCIES` (по умолчанию `GRAM,TRX`): сумма в них считается по курсу xRocket (`GET /api/v1/rates`) в момент выставления счёта и округляется вверх. Пользователь выбирает валюту в «Тайник Премиум». Коды, которых нет в списке валют xRocket, сервер при запуске убирает и пишет об этом в журнал.
3. `docker compose up -d`. В журнале появится «подписка включена (xRocket Pay)».

Адрес вебхука `https://DOMAIN/api/pay/xrocket` сервер сам передаёт в каждом счёте (нужен `DOMAIN` в `.env`); можно указать его и в настройках приложения xRocket. Если вебхук не дошёл, оплату всё равно найдёт сверка: кнопка «Проверить оплату» у пользователя и фоновая проверка неоплаченных счетов раз в 5 минут. Проверить всё без настоящих денег: токены из тестового бота [@xrocket_testnet_bot](https://t.me/xrocket_testnet_bot) и `XROCKET_TESTNET=1`.

В панели администратора — число подписчиков, последние счета и кнопка «Дать премиум» / «Премиум…» у каждого пользователя: продлить на N дней (подарок, оплата, которую не удалось подтвердить автоматически) или отключить (0).

Как устроено:
- Деньги приходят на баланс вашего приложения в @xRocket (за вычетом комиссии xRocket). Вывод — там же.
- В xRocket уходит только сумма, валюта, срок тарифа и случайный номер счёта — **юзернейм пользователя туда не передаётся**. Сервер Тайника не видит кошелька плательщика.
- Вебхук принимается только с верной подписью HMAC-SHA256 (Webhook Token) и не старше 5 минут; сумма и валюта сверяются с выставленным счётом. Один счёт продлевает подписку ровно один раз, сколько бы уведомлений ни пришло. Продление добавляет дни к текущему сроку.
- Фото профиля, как имя, лежит в **зашифрованном** профиле и уходит только собеседникам. Сервер знает лишь, у кого есть подписка: этот признак видят собеседники (звезда), и фото показывается, только пока подписка действует.
- Ограничение: фото — маленькое (160×160, до ~15 КБ), оно встроено в профиль. На новое устройство при привязке переносятся фото недавних собеседников (сколько помещается в канал привязки), остальные появятся, когда собеседник обновит профиль.

## Что хранит сервер

| Данные | Можно ли прочитать |
|---|---|
| Имена и публичные ключи | Да, они публичные по смыслу |
| Недоставленные сообщения | **Нет**, это шифротекст. Удаляются после доставки или через `QUEUE_TTL_DAYS` дней |
| Вложения (фото, видео, файлы) | **Нет**: шифруются на устройстве отправителя, ключ есть только у собеседников. Сервер знает лишь размер. Удаляются через `QUEUE_TTL_DAYS` дней, лежат в `data/blobs` |
| Чёрные списки пользователей | Да: кто кого заблокировал. Без этого сервер не смог бы не доставлять сообщения заблокированных |
| Подписки Web Push | Адрес push-сервиса и ключи браузера для каждого устройства, где включены уведомления |
| Журнал контейнера | В нём нет имён, IP и содержимого |
| Последний IP каждого устройства | Да: виден администратору в панели и самому пользователю в «Устройствах». Удаляется вместе с устройством |
| Заблокированные IP | Да, список с заметками администратора |
| Подписка «Премиум» и счета | Да: до какого числа действует подписка, счета (тариф, сумма, статус, время). Признак подписки видят собеседники. Фото профиля сервер не видит — оно зашифровано |
| Журнал запросов nginx для этого сайта | Отключён |

Сервер видит **метаданные**: кто, кому и когда пишет.

После изменения `.env` выполните `docker compose up -d`.

## Сервер без nginx

Если портов 80 и 443 никто не занимает, можно обойтись без nginx и запустить Caddy, который сам получит HTTPS-сертификат:

```bash
cp .env.example .env && nano .env    # DOMAIN, ACME_EMAIL
docker compose -f docker-compose.yml -f docker-compose.caddy.yml up -d --build
```

Есть и вариант без Docker: `deploy/tainik.service` (systemd, нужен Node.js 22.13+).

## Если что-то не работает

| Симптом | Причина и решение |
|---|---|
| Скрипт: «В nginx уже есть сайт с server_name …» | Домен уже занят другим сайтом. Используйте другой поддомен или уберите старый сайт. |
| `certbot` не выпустил сертификат | Нет A-записи или порт 80 закрыт снаружи. После исправления выполните `certbot --nginx -d домен`. |
| Веб открывается, но статус «нет связи» | Проверьте, что в `tainik.conf` есть `Upgrade`/`Connection` и что после certbot они остались в блоке `listen 443`. |
| Сборка: `TLS handshake timeout` / `failed to resolve source metadata` для `node:22-alpine` | Нет связи с Docker Hub — см. ниже. |
| В браузере «Нужен защищённый контекст» | Сайт открыт по `http://` или по IP. Откройте по `https://домену`. |

### Docker Hub недоступен

Ошибка `TLS handshake timeout` при сборке означает, что сервер не может достучаться до Docker Hub (бывает временно или из-за ограничений у хостера). Подключите зеркало:

```bash
cat /etc/docker/daemon.json 2>/dev/null   # если файл есть — добавьте ключ в существующий JSON
echo '{ "registry-mirrors": ["https://mirror.gcr.io"] }' | sudo tee /etc/docker/daemon.json
sudo systemctl restart docker             # контейнеры с restart: unless-stopped поднимутся сами
docker pull node:22-alpine                # проверка
```
