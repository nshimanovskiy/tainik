# Тайник: E2E-мессенджер (протокол v3: X3DH + Double Ratchet, несколько устройств)

[English](README.md)

Это мессенджер со сквозным шифрованием, у которого есть **веб-версия** и **десктопная** (Windows, macOS, Linux). Сервер видит только шифротекст. Интерфейс и крипто-ядро у обеих версий общие. Один аккаунт можно открыть на нескольких устройствах (до 5): например, на компьютере в приложении и в браузере на ноутбуке.

## Быстрый старт

```bash
node --version            # нужен Node.js 22.13+ (встроенный SQLite)
npm start                 # сервер + веб-клиент: http://localhost:8080
npm test                  # 22 автотеста: протокол, клиент↔сервер, устройства, сервер, десктоп
```

Чтобы проверить вдвоём на одном компьютере, откройте `http://localhost:8080` в обычном окне и в окне инкогнито, зарегистрируйте два имени и добавьте друг друга.

> WebCrypto работает только по `https://` или на `localhost`.

**Деплой на VPS** (Docker за вашим nginx, HTTPS через certbot, бэкапы) описан в **[DEPLOY.md](DEPLOY.md)**. Коротко: `sudo ./deploy/setup.sh chat.example.com you@example.com`.

## Десктопная версия (Electron)

```bash
npm start                 # в корне: запустить сервер
cd desktop
npm install               # скачает Electron и electron-builder
npm start                 # запустить приложение
npm run dist              # собрать установщик для текущей ОС → desktop/dist/
```

При первом запуске укажите адрес сервера: `ws://localhost:8080/ws` для локальной проверки или `wss://ваш-домен/ws` для боевого сервера.

**Выпуск на GitHub.** Actions → «Выпуск десктопа» → Run workflow (или тег `v0.7.0`): workflow `release.yml` соберёт установщик и переносной `.exe`, `.dmg` (Apple Silicon и Intel), `.AppImage` и `.deb` и опубликует релиз с контрольными суммами. Подробно — в **[RELEASING.md](RELEASING.md)**.

**Защита в десктопе:**
- Ключи, сессии и переписка лежат в одном файле, зашифрованном системным хранилищем ОС через `safeStorage`: Keychain на macOS, DPAPI на Windows, libsecret/KWallet на Linux.
- Если на Linux нет связки ключей, приложение честно предупредит об этом.
- Страница работает в песочнице: `contextIsolation`, `sandbox`, без Node.js. Код загружается из самого приложения по протоколу `app://`, а не с сервера, поэтому взломанный сервер не может подменить JavaScript. Это главное преимущество перед веб-версией.
- Запускается только одна копия приложения, переходы и новые окна запрещены, включены Electron fuses (`runAsNode` выключен, есть проверка целостности asar).
- Сборки **не подписаны**. Windows SmartScreen и macOS Gatekeeper покажут предупреждение. Для распространения нужны сертификат Authenticode (Windows) и Apple Developer ID с нотаризацией (macOS).

## Ответы, удаление, статус

- **Ответ с цитатой**, как в Telegram: ↩︎ при наведении, правый клик или долгое нажатие. Цитата шифруется вместе с сообщением, поэтому её видят и устройства, на которых нет оригинала.
- **Удаление:** «у меня» удаляет сообщение на всех ваших устройствах, «у всех» удаляет и у собеседника. Это любые сообщения в личном чате, как в Telegram. Команды удаления передаются зашифрованными. Удалённое не появится снова, даже если его копия придёт с опозданием.
- **Статус:** «в сети» или «был(а) …» с мгновенным обновлением. Свой статус можно скрыть (⋯ → «Показывать другим, что я в сети»). Тогда другие видят «был(а) недавно». Сервер знает, когда вы в сети: это метаданные.

## Уведомления и работа в фоне

- **Десктоп** работает в фоне: крестик прячет окно в трей, соединение остаётся, сообщения и звонки приходят. В меню значка в трее — «Открыть», «Запускать при входе в систему», «Выйти». При автозапуске приложение стартует без окна. Отключить фоновый режим: ⋯ → «Работа в фоне». Число непрочитанных показывается на значке приложения. Входящий звонок показывает окно, не перехватывая фокус.
- **Веб**: при первом входе Тайник предложит включить уведомления. Пока вкладка открыта, уведомления показывает сама страница. Когда вкладка закрыта, сервер будит браузер через **Web Push** (VAPID + шифрование RFC 8291, без внешних библиотек). Push-сервис браузера (Google, Mozilla, Apple) видит только факт и время пуша: имя отправителя зашифровано для вашего браузера, а текста сообщения в пуше нет вовсе (сервер его не знает). Звонок, который никто не принял, приходит как «Пропущенный звонок». На iPhone и iPad пуши работают, только если добавить Тайник на экран «Домой».
- По умолчанию в уведомлении **нет текста** сообщения, только имя собеседника. Показ текста включается в ⋯ → «Уведомления»; это касается только открытого приложения или вкладки.
- Клик по уведомлению открывает нужный чат.

## Звонки

Голосовые и видеозвонки один на один с трансляцией экрана.
- **Медиапоток** идёт напрямую между устройствами и шифруется DTLS-SRTP. **Данные соединения** (SDP с отпечатком DTLS-сертификата) передаются эфемерными сообщениями Double Ratchet: они не попадают в очередь и не сохраняются. Поэтому сервер не может встать посередине звонка.
- Звонок приходит **на все устройства** собеседника. Ответ на одном устройстве останавливает звонок на остальных.
- Три фиксированных трансивера (звук, камера, экран): камеру и экран можно включать и выключать без повторного согласования соединения. Состояние и завершение звонка передаются по DataChannel.
- **Через NAT** звонки проходят с помощью TURN-сервера (coturn): `sudo ./deploy/setup-calls.sh`. Сервер выдаёт временные учётные данные (HMAC, 12 часов, без имени пользователя), а пересылка во внутренние сети запрещена. TURN видит только зашифрованные пакеты.
- Во время прямого звонка собеседники видят IP-адреса друг друга.

## Несколько устройств

**Как привязать:**
1. На **новом** устройстве откройте вкладку «Привязать устройство» и нажмите «Показать код». Появятся QR-код и 64-символьный код.
2. На **уже привязанном** устройстве откройте **⋯ → Устройства и привязка**, отсканируйте QR (там, где браузер умеет работать с камерой) или введите код.
3. Новое устройство получит ключ личности и контакты (с отметками «проверен») и зарегистрируется как ещё одно устройство аккаунта. Старая переписка не переносится.

**Как это устроено (модель Signal):**
- У аккаунта **одна личность**, поэтому код безопасности у собеседников не меняется, когда вы добавляете устройство.
- У каждого устройства **свои** prekey и **свои** сессии Double Ratchet со всеми устройствами собеседников.
- Каждое сообщение шифруется **отдельно для каждого устройства** получателя, а копия уходит **остальным вашим устройствам**, поэтому отправленное с ноутбука видно и на компьютере.
- Сервер сверяет список устройств при каждой отправке. Если устройство добавилось или исчезло, клиент сам обновит список, установит недостающие сессии и отправит заново.
- **Канал привязки:** код содержит одноразовый публичный ключ нового устройства и передаётся мимо сервера (глазами или камерой). Посылка с ключами шифруется под этот ключ (X25519 → HKDF → AES-GCM), поэтому сервер её не прочитает и не подменит. Код действует 10 минут и срабатывает один раз.
- **Отвязка:** ⋯ → Устройства → «Отвязать». Сервер удаляет устройство и его очередь, а само устройство при следующем подключении стирает свои ключи и переписку.

## Протокол v3

Протокол реализован по спецификациям Signal: [X3DH](https://signal.org/docs/specifications/x3dh/) и [Double Ratchet](https://signal.org/docs/specifications/doubleratchet/).

| Элемент | Как устроено |
|---|---|
| Личность | X25519 (для DH) + Ed25519 (для подписей). Вместо XEdDSA используются две пары; обе входят в AD и в код безопасности. |
| Prekeys | Подписанный prekey (ротация раз в 7 дней, старые хранятся ещё 30 дней) и 100 одноразовых. Каждый одноразовый ключ сервер выдаёт только один раз. Когда их остаётся меньше 20, клиент догружает новую партию. |
| X3DH | Даёт возможность начать переписку, даже если собеседник офлайн. SK = HKDF(F ‖ DH1 ‖ DH2 ‖ DH3 ‖ DH4). Подпись signed prekey проверяется. |
| Double Ratchet | Новый ключ на каждое сообщение и DH-храповик на каждом «повороте» диалога. Пропущенные и перемешанные сообщения обрабатываются (до 1000 в одной цепочке). |
| Адресация | Сессия устанавливается между парой **устройств** («alice.1» ↔ «bob.2»). Номера устройств входят в AD X3DH и в AAD каждого сообщения. |
| Шифр | AES-256-GCM. AAD = AD сессии ‖ заголовок ‖ (версия, отправитель и его устройство, получатель и его устройство, id). Текст дополняется до кратного 64 байтам. |
| Вход на сервер | Пароля нет: клиент подписывает случайный nonce ключом Ed25519. |
| Проверка ключей | TOFU плюс код безопасности из 60 цифр. Если ключ собеседника сменился, отправка блокируется до явного подтверждения. |

**Свойства, проверенные тестами:** forward secrecy (использованные ключи удаляются, повтор отклоняется); восстановление после компрометации (украденное состояние не читает новые сообщения после DH-шага); подмену шифротекста, заголовка и id; повтор первого сообщения после уничтожения OPK; поддельную подпись SPK; подмену ключа сервером; одновременный старт сессий с двух сторон; перемешанную доставку и потерянные сообщения; отсутствие открытого текста на диске сервера; изоляцию копий между устройствами; привязку устройства (неверный, чужой, устаревший или изменённый код отклоняется); синхронизацию отправленных; отвязку. QR-генератор проверен декодером OpenCV на версиях 1–10.

### Переход на libsignal

`shared/protocol/session.js` повторяет модель libsignal: функции `startSession` / `encrypt` / `decrypt` и хранилище из шести методов (`getLocalIdentity`, `getSignedPreKey`, `getOneTimePreKey`, `removeOneTimePreKey`, `loadSession`, `storeSession`). Чтобы перейти на `@signalapp/libsignal-client` (npm, лицензия AGPL-3.0), нужно переписать только этот файл, используя `processPreKeyBundle`, `signalEncrypt` и `signalDecrypt(PreKey)`. Интерфейс и сервер менять не придётся.

## Ограничения (честно)

1. **Протокол — собственная реализация по спецификации, а не libsignal.** Она покрыта тестами, но не проходила аудит. Перед реальным запуском либо замените её на libsignal (см. выше), либо закажите независимый аудит.
2. **Отвязка не равна отзыву ключа.** У отвязанного устройства был ключ личности. Если устройство **украдено**, злоумышленник не получит новых сообщений (сервер его больше не пускает), но с этим ключом сможет зарегистрировать новое «устройство» вашего аккаунта. Надёжный выход в этом случае — создать новый аккаунт: собеседники увидят смену ключа. Автоматической смены личности пока нет (у Signal похожая модель).
3. **В вебе** локальная база зашифрована ключом, который браузер хранит в том же профиле. Это защищает от случайного чтения файлов, но не от полноценного доступа к компьютеру. Кроме того, веб-клиент получает код с сервера. Для серьёзной защиты используйте десктоп.
4. **Метаданные** (кто, кому и когда пишет) серверу видны.
5. Нет групповых звонков, групп и файлов. Web Push идёт через push-сервис производителя браузера: он узнаёт, *когда* вам пишут (но не кто и что). Нет резервного копирования ключей пользователей (бэкап сервера есть, но ключи живут только на устройствах).
6. Данные версий v1 и v2 несовместимы с v3, аккаунты создаются заново.
7. **История переписки** на новое устройство не переносится, синхронизируются только новые сообщения.
